# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

Apify Media Data Ingestion & Normalization Pipeline. Scrapes media/social data via Apify actors, normalizes it through a declarative schema system, and sends it to downstream services (RabbitMQ).

## Architecture

### Schema System (`src/schema/`)
Declarative, multi-stage data normalization framework:
- **`parse_object.py`** — Core `Parser` class that orchestrates: structure parsing (flatten/nest) → type conversion → default application → validation. Recurses into nested objects and into list-of-composite fields (see below) via `traverse_nested`.
- **`types.py`** — Type-specific parsers (`IntParser`, `FloatParser`, `StrParser`, `BoolParser`, `DateTimeParser`, `UrlParser`, `EnumStrParser`, `ListParser`) with parse/validate methods. Also exposes `extract_list_object_type(field_type)` which detects the `"List[Name]"` string syntax used to declare lists of composite items.
- **`schemas/news.py`** — NEWS_SCHEMA for articles/posts. `news_types = ["news", "x", "facebook", "impreso", "instagram", "linkedin", "radio", "tv"]` — the intermediate `type` field carries the actual platform and is validated by `EnumStr` against this list. Includes `location_ids` field (type list) for geocoded geoids, `location_author` (type `"LocationAuthor"`) as a nested object carrying author location fields, and `comments` (type `"List[Comment]"`) for per-post comment lists. Also defines `LOCATION_AUTHOR_SCHEMA` (unprefixed keys: `formatted_name`, `geoid`, `coords` (LocationCoords), `precision_level`, `level_1`/`level_2`/`level_3` and their `*_id` counterparts) and `COMMENT_SCHEMA` (`comment_text`, `comment_author`, `comment_author_url` — commenter profile URL, added 2026-07-21 to unblock WS-4 profile enrichment; scrapers return it, mappers now keep it — `comment_timestamp`, `comment_likes`) — each comment item is fully normalized: timestamps are parsed to `datetime`, likes are coerced to `int`. `require_url` reads `obj.get("type")` on the News record (URL required unless `type == "impreso"`). The intermediate `Document.data` still holds author location as flat `location_author_*` keys; `Document.to_final_schema()` collapses them (strips prefix) into the nested `location_author` dict before running `normalize_record`.
- **`schemas/source.py`** — SOURCE_SCHEMA for news sources/websites with crawl configuration

Key patterns: schemas support nested objects, `"List[CompositeType]"` string-typed lists of nested objects (e.g. `"comments": {"type": "List[Comment]"}`), context-aware default callbacks, conditional validation (e.g., URL required only when type != "impreso"), and timezone-aware datetime handling (Mexico City timezone).

### Models (`src/models/`)
Document hierarchy and source management:
- **`document.py`** — Base `Document` class. Holds intermediate schema data as `self.data` dict with `language` and `comments` fields. Provides `_empty_data()` (all intermediate fields as None/[], including `comments: []`), `detect_language()` (detects via `langdetect` and caches in `data["language"]`), `matches_language(code)`, `matches_min_date(dt)`, `matches_location(country_id)` (checks `location_ids` first — any geoid prefix match keeps doc; falls back to `author_location_id` when `location_ids` is empty; docs with no location data are kept), and `add_locations()` (writes geocoding results to `location_ids`; only writes author location fields if currently None, preserving SourcesManagement data) for pipeline filtering. Concrete `to_final_schema()` parses `self.data` against `NEWS_SCHEMA` and returns `{"type": "news", "message": parsed}` — the envelope type is always `"news"`; the inner `message.type` carries the platform.
- **`news.py`** — `News(Document)`. Represents a news article. `from_url(url)` class method creates a News from any URL, fetches and parses it, sets `data["source"]` via `SourcesManagement.get_source_name(domain)` when not already populated, returns News or None. `from_google_news(item)` class method creates a News from raw Apify dict (pure data mapping, no enrichment). `fetch_and_parse()` downloads HTML via `fetch_html()` (unpacking the `(html, final_url)` tuple), updates `self.data["url"]` to the final URL when it differs from the original (handling shortened/redirected URLs), then extracts content via `extract_article()` using the final URL, and updates `self.data` (title, body, author, media_urls, timestamp — only overwriting when the parser returned a non-empty value). `enrich_location(sources)` sets ALL author location fields (`location_author_formatted_name`, `location_author_geoid`, `location_author_coords`, `location_author_precision_level`, `location_author_level_1`/`level_2`/`level_3` and their IDs, plus `author_location_text`/`author_location_id`) from `SourcesManagement` domain lookup and tracks unknown sources. News articles do NOT geocode — location comes from SourcesManagement only. Uses the inherited `Document.to_final_schema()` (`type="news"` intermediate → envelope `{"type": "news", "message": parsed_news}`).
- **`post.py`** — Base `Post(Document)` class for social media posts. An attached URL that fetches but parses with an **empty body** (dead or truncated link, e.g. `http://3.er/`) is dropped with a warning — not attached, not appended — since publishing it fails schema validation ("Missing required field: body"); shared by the worker and `run_searches.py`. Overrides `to_final_schema()` to fill post-specific fallbacks (body, title, `fb_likes`) before delegating to `super().to_final_schema()` for schema parsing and envelope wrapping. Platform-specific subclasses handle data mapping and set `data["type"]` to the platform: `instagram`, `facebook`, `x`, `linkedin`. Shared `UsersManagement` singleton caches user profile data. Attribute: `attached_news: News | None` (initialized to `None`) stores the `News` object created when a linked article is fetched. Methods: `fetch_attached_url(url=None)` — when `url` is provided it is used directly; otherwise falls back to `self._raw.get("link")` (e.g. Facebook's `link` field) or the first external URL in the post body. Fetches and parses via `News.from_url()`, appends article text as `\n\n attached_url_text: <text>`, optionally copies source location to the post, stores the resulting `News` object on `self.attached_news`, and falls back to the parent post's `timestamp` when the fetched article still has no `timestamp` after parsing (the parser surfaces a date when one is present in the HTML, but some articles lack it) so the attached news isn't published with a null date. `_extract_first_external_url()` finds the first non-platform URL in the body. `enrich_location()` (geocode with UsersManagement cache), `needs_user_author_update(max_age_days)`, `apply_cached_user_author()` (applies cached `website_visits`, `author_full_name`, `author_profile_bio`, and `author_location_text`), `save_user_author_stats(stats)` (also writes `author_location_text` when present in stats). Intermediate schema includes `author_full_name` and `author_profile_bio` fields.
- **`instagram_post.py`** — `InstagramPost(Post)`. `from_instagram(item)` class method creates from raw Instagram Apify result, mapping caption, media URLs (via `_collect_media_urls`), engagement metrics, profile URL, and post type (Image, Sidecar, Story, Reel). `from_instagram_queenlike(item)` class method creates from a `queenlike_xystos/instagram-posts-reels-scraper---no-cookies` result: `taken_at` (epoch) → ISO `timestamp`, `caption` → `body`, `like_count` → `likes`, `reshare_count` → `shares` (the queenlike scraper actually returns share counts, unlike the default Instagram actors), `comment_count` → `n_comments`, `play_count` → `views`, `author.full_name`/`author.username` → `author`/`author_full_name`/`profile_url`, `author.follower_count` → `website_visits` (already embedded — no profile scrape needed for follower count). Post type is inferred via `_infer_queenlike_post_type` (`product_type=clips`/`reel` → Reel, `carousel_media`/`children` → Sidecar, `video_url` → Video, else Image). Media URLs collected via `_collect_queenlike_media_urls` (`video_url`, `thumbnail_url`, `image_url`, `display_url`, plus recursive `carousel_media`/`children`). In both mappers `source` carries the **account name** (full name, then username, falling back to `"Instagram"`) — the platform lives in `type`/`news_type`, and `source` must stay per-account so source-scoped searches and facets work (same convention as Facebook/X/LinkedIn and `TikTokPost.from_tiktok`, which uses nickname → username → `"TikTok"`).
- **`facebook_post.py`** — `FacebookPost(Post)`. `from_facebook(item)` class method creates from raw Facebook Posts Scraper result, mapping text, media (with OCR text appended as `image_text_N`), engagement metrics, and page name extracted from URL. Facebook post types: Photo, Video, Reel, Status. `from_facebook_search(item)` class method adapts `scrapeforge/facebook-search-posts` output to the same intermediate schema. Field mapping: `message_rich`/`message`/`text`/`content` → `body`; `timestamp` (epoch) → ISO `timestamp`; `reactions_count`/`likes_count`/`reactions.like` → `likes`; `reshare_count`/`shares_count` → `shares`; `comments_count` → `n_comments` (zero-safe via `_first_not_none()` so 0 isn't coerced to None); `author.name`/`author.url` → `author`/`profile_url`; `external_url` → carried on the raw object and passed explicitly into `Post.fetch_attached_url(url=…)` by `FacebookKeywordSearchActor._enrich_content`. `_infer_facebook_search_post_type()` checks `video`/`video_files`/`video_url`/`videos` → Video, then `image`/`image_url`/`images`/`album_preview` → Photo, else Status. `_collect_facebook_search_media_urls()` reads `image`, `video`, `thumbnail`, `video_thumbnail` (string fields), `album_preview[].image_file_uri`, `images[]`, and `video_files[]`/`videos[]`.
- **`twitter_post.py`** — `TwitterPost(Post)`. `from_twitter(item)` class method creates from raw `api-ninja/x-twitter-advanced-search` tweet: `body=full_text/text`, `author=user.name`, `author_profile_bio=user.description`, `author_location_text=user.location`, `profile_url=https://x.com/{screen_name}`, engagement metrics (likes, retweets, replies, views), media URLs from entities, and post type (original/reply/retweet/quote). Since bio and location come embedded in the tweet, `TwitterKeywordSearchActor` skips the `_enrich_user_author` stage entirely. Helpers: `_infer_tweet_type()`, `_collect_tweet_media_urls()`.
- **`linkedin_post.py`** — `LinkedInPost(Post)`. `from_linkedin(item)` class method creates from raw `harvestapi/linkedin-post-search` post: `body=text/content`, `author=author.name`, `author_profile_bio=author.headline`, `author_location_text=author.location`, `profile_url=author.linkedinUrl`, engagement metrics (`reactionsCount`/`repostsCount`/`commentsCount`), media URLs from `post.media`, and post type (video/image/text). `website_visits` is populated with `author.followersCount` when present (i.e. when `profileScraperMode="main"`). Helpers: `_infer_linkedin_post_type()`, `_collect_linkedin_media_urls()`.
- **`sources_management.py`** — `SourcesManagement` class. Single interface for all source-related operations. Reads sources from MongoDB (via `src/helpers/mongoconnection.py`) at module load and builds `_known_sources` set, `_domain_country_id` dict, and `_domain_source_name` dict (domain → `sitio`). If MongoDB is unavailable at load time, it uses an explicit empty catalog: news source/location enrichment is skipped, Mongo-backed source names/locations are not applied, and `cache/unknown_sources.json` is not updated. Methods: `get_domain(url)` extracts domain (tldextract-backed, strips `www` and ports), `is_known(domain)` checks known sources, `get_country_id(domain)` returns country_id (first 4 chars of `geoid`), `get_source_name(domain)` returns the known `sitio` or falls back to the domain name without TLD (e.g. `elfinanciero.com.mx` → `elfinanciero`), `get_location(domain)` and `_build_domain_location()` return a full location dict with all author location fields (`location_author_formatted_name`, `location_author_geoid`, `location_author_coords`, `location_author_precision_level`, `location_author_level_1`/`level_2`/`level_3` and their IDs), 
- **`news_parser/`** — Article enrichment pipeline (moved from `src/actors/news/news_parser/`):
  - **`load_url.py`** — `fetch_html(url)`: streaming HTTP download with size guard (10MB), retry, and browser UA headers. Returns a tuple `(html, final_url)` where `final_url` is the URL after following redirects (`r.url` from requests). Returns `(None, None)` on failure. **Timeouts are split** into a short `CONNECT_TIMEOUT` (10s, so dead/unroutable hosts fail fast and don't tie up an attempt) and a generous, per-attempt-escalating read timeout `READ_TIMEOUTS = (90, 120, 150)` (passed as `timeout=(connect, read)`); the same per-attempt read budget also caps total streaming time. Because a read timeout is only an upper bound on inter-byte wait, fast servers still return in their natural time — the generous first-attempt read budget costs them nothing while letting slow-but-succeeding origins behind slow CDNs (e.g. `oem.com.mx`, ~80s time-to-first-byte) succeed on the **first** attempt instead of dying on the old flat 15s cap and burning ~2 min across retries. `REQUESTS_TIMEOUT` is retained as an alias for `READ_TIMEOUTS[0]` for backwards compatibility. **Client-side redirects are followed too**: `fetch_html` now wraps `_fetch_html_once` (the HTTP-3xx-only fetch) in a bounded loop (`MAX_CLIENT_REDIRECTS` = 3, visited URLs tracked so a self-referencing stub can't loop) that detects JS/meta-refresh interstitials via `_extract_client_redirect` and re-fetches the target, so `final_url` is the real article. This is what X's `t.co` serves — HTTP **200** with ~400 bytes of `<META http-equiv="refresh">` + `location.replace("https:\/\/…")`, never a 3xx — so without it every tweet's attached article was fetched as a contentless stub and stored under the shortener URL as its ES `_id`. Only responses ≤ `MAX_INTERSTITIAL_SIZE` (4096 bytes) are inspected, so a real article that happens to contain a meta-refresh (cookie wall, "page has moved" banner) is never redirected away from its own content; JS string escapes (`\/`) are unescaped and relative targets resolved with `urljoin`.
  - **`parser.py`** — `extract_article(html, url)`: **multi-tier content extraction**, deterministic tiers first so full clean bodies come back instantly and the slow (~3 min) LLM tier stays a last resort. Cascade order:
    1. **Generic JSON-LD `articleBody` tier** (`_try_jsonld`) — scans all `application/ld+json` scripts (flattening top-level arrays and `@graph`) for the first `NewsArticle`/`Article`/`ReportageNewsArticle`/`BlogPosting`/… node (`_ARTICLE_LD_TYPES`) with a non-trivial `articleBody` (>= `MIN_JSONLD_BODY_LENGTH` = 200 chars); returns `{title=headline, body=articleBody, author, media_urls=image url(s), timestamp=datePublished}` directly. Site-agnostic; wins for any outlet that ships a full `articleBody`.
    2. **Domain-keyed extractor registry** (`_try_domain_extractor` → `_DOMAIN_EXTRACTORS`, mapping registrable domain → extractor). Entries: `revvialibre.com.mx` → `_extract_revvialibre` and `oem.com.mx` → `_extract_oem`. `_extract_revvialibre` parses Revista Vía Libre's static PHP template (`noticias.php?noticia=N`) with BeautifulSoup: the article column is `section.bg-white .col-md-8` — `h2` → title, `div.text-center img` → lead image, and `div.text-justify` → body, whose first inner `<div>` is the byline (`author&nbsp;dd/mm/yyyy`, split by `_VIALIBRE_BYLINE_RE` into `author` + an ISO `timestamp`, then extracted so it doesn't prefix the body). The site ships no JSON-LD, and NewsPlease instead returns the "Patrocinadores" sidebar + teaser-card grid, which slips past `_looks_like_related_posts_list` because only two "Leer Más" links survive extraction (the guard needs 3) — hence a deterministic extractor rather than a guard tweak. Falls through (`None`) when the layout doesn't match or the body is under `MIN_BODY_LENGTH`. `_extract_oem` parses OEM's (Organización Editorial Mexicana) Next.js **RSC flight stream** (`self.__next_f.push([1,"…"])` chunks — the visible DOM only holds related-article sidebars, and OEM JSON-LD has no `articleBody`). It JSON-string-unescapes each chunk (correct UTF-8 accents — never `unicode_escape`, which mojibakes `año`→`aÃ±o`), collects every `storyline_paragraph` value node in document order pairing each with its enclosing node's `publishedAt`, keeps only paragraphs whose date matches the article's (JSON-LD `datePublished`, else the mode — this drops the trailing author-bio card carrying a different date), drops the injected newsletter CTA and verbatim repeats, reassembles the body, and validates extracted word count against JSON-LD `wordCount` (rejects a fragment < 0.3×). Metadata (title/author/date/image) comes from JSON-LD. Returns `None` on any failure so the cascade continues unchanged.
    3. **NewsPlease** (+ `newspaper4k` gap-fill), guarded by `_has_meaningful_content` / the related-content guards below.
    4. **LLM fallback** (via `src/oai/llm_core.py`) when everything above fails — **gated on the page having readable text**: `_parse_with_llm` returns `None` immediately when `_visible_text_length(html)` (tags, `script`/`style`/`noscript` stripped) is under `MIN_BODY_LENGTH`. Handed a contentless stub the model does not return null, it **invents** an article — a `t.co` interstitial produced a fully-formed "Biden administration announces new student loan forgiveness plan" that would have been published under the shortener's URL. Nothing to read means nothing to extract, so the tier fails honestly instead.
    Both deterministic tiers log at INFO which tier produced the body (so tier usage is measurable in run logs). Returns `{title, body, author, media_urls, timestamp}` or None. `timestamp` is sourced from JSON-LD `datePublished`, NewsPlease's `date_publish`, newspaper's `publish_date`, or the LLM's `published_at` field (ISO 8601), and may be a `datetime` or string — the schema's `DateTimeParser` accepts both. Requires body >= 200 chars for meaningful content. `_has_meaningful_content` also rejects bodies whose text looks like a related-posts list, via two heuristics that force the LLM tier: (1) `_looks_like_related_posts_list` — 3+ case-insensitive hits of "Ver más"/"Leer más"/"Read more"/"See more"/"Continue reading"/"Saber más"/"Más información" (catches WordPress page-builder loop blocks, e.g. Breakdance `bde-loop-item`/`ee-post-content`); (2) `_looks_like_section_label_list` — catches the OEM (Organización Editorial Mexicana) variant that evades (1): the extracted "body" is a stack of `SECTION\nHeadline\nDek` triples, so it fires when known section-label lines (LOCAL/POLICIACA/CULTURA/DEPORTES/FINANZAS/NACIONAL/... — see `_SECTION_LABELS`) appear as standalone lines 3+ times, **or** any short line (<=40 chars) repeats verbatim 3+ times. Both are structural signals (label alone on its own line / verbatim repetition), so a real article merely mentioning those words inline is not rejected.

### Actors System (`src/actors/`)
Apify actor integrations for data scraping:
- **`actor.py`** — Base `ApifyActor` class. Wraps `ApifyClient`, provides `run_actor()` for executing actors, and `process_documents(docs, **kwargs)` — a staged pipeline that runs: `_filter_keywords` → `_filter_date` → `_enrich_content` → `_filter_language` → `_enrich_user_author` → `_enrich_location` → `_filter_location` → `_filter_llm` → `_enrich_comments`. User author enrichment runs before location so that cached profile data (including `author_location_text`) is available for geocoding. Subclasses can override `process_documents()` to change the pipeline order (e.g. Instagram overrides to run location before user author). `_filter_keywords` filters out documents matching any `not_keywords` (case-insensitive substring on body+title). `_filter_date` resolves `period` (d/w/m) to `min_date` if no explicit `min_date` is given. `_filter_llm` caches each document's keep/drop decision per `(url, condition, snippet_max_len)` (via `cache_get`/`cache_set` in `src/oai/llm_core.py`, tag `llm_filter`, field `keep`): documents with a cached decision are resolved up front and only undecided ones are sent to the LLM, batched (`LLM_FILTER_BATCH_SIZE`) with snippets (keyword-context or first 250 chars) under a Spanish-language `llm_filter_condition`; the LLM returns the indices to keep and each new decision is written back. Because the key is URL-based (not batch-based), a decision is reused regardless of batching and shared across tasks with the same condition; `override_filters=True` bypasses the cache read and re-evaluates. URL-less docs are never cached. The batch call itself still uses `llm_cached_call` (tag `llm_filter_batch`) as a content-addressed fallback. `search_params` is stored as `self.search_params` by each actor's `search()` for keyword-context snippet extraction. **Batch runs** (`self.batch`, a `src/worker/batch.py::BatchContext` set by the worker; None otherwise): `_filter_cached_documents` also skips URLs cached as dropped under any member's key, `_remember_filter_decisions` (the single cache-write path every `process_documents` ends with) also writes the matching members' keys, and `_count_pipeline_input` feeds the per-member attribution. `_enrich_user_author` is no-op by default; subclasses override to enrich posts with author profile data. Cached user stats are always applied regardless of `enrich_followers` flag; the flag only gates the expensive Apify scraping call. `_enrich_comments` is no-op by default; subclasses override to scrape comments via dedicated actors. Defines the interface: `search(search_params, **kwargs)`. Subclasses must set `actor_id`. **Run funnel** (2026-10-06, for `crawl_runs`): `funnel` (a `Counter`, reset by `reset_funnel()`, accumulated per actor instance) counts `docs_in` — documents entering the pipeline, counted in `_filter_cached_documents`, which every `process_documents` (base and overrides) calls first — and `dropped_<reason>` for every reason `_record_filtered_documents` sees (`cached`, `keyword`, `date`, `existing_elasticsearch`, `language`, `location`, `llm_filter`); `funnel_newest`/`funnel_oldest` hold the timestamp span of `docs_in`. `_gate_by_likes(documents, threshold, stage)` is the shared `*_after_likes` gate (posts with `likes` > threshold; `None` = all) and counts the posts it skips as `<stage>_skipped_likes` (`comments` / `profiles`). Purely in-memory and cheap; `run_searches.py` ignores it.

It must stay byte-identical to the backend's `crawl_helpers.adhoc_cache_key`; both suites pin the same test vector.

### Social-account characterization (WS-4)

A read-time classification layer for social authors: a Mongo-backed per-account store plus a batch classifier that harvests evidence from Elasticsearch, computes deterministic features, optionally joins userdb sentiment, and LLM-classifies only accounts with enough activity. **Reports look accounts up in Mongo at read time and join them onto the (immutable) ES documents — nothing is written to ES.** Grounding: `reports/event_report/docs/social_report_design.md` §1 and `business_agent/customers/sjdr/plan.md` WS-4.

- **`src/models/social_users.py`** — `SocialUsers`, a CRUD wrapper over the `SocialUsers` Mongo collection (same DB as `CrawlersAll`; name from `MONGO_DB_NEWS_SOURCES`, reuses `src/helpers/mongoconnection.py`). **Two-tier identity, one document per account**: tier `"profile"` (post authors) keyed by a canonical, normalized `profile_url`; tier `"name"` (comment-only authors) keyed by `(network, normalized_name)` where `normalize_name` casefolds, collapses whitespace and strips accents. Name-tier records carry a lower `identity_confidence` ceiling (best-effort display-name identity). `account_id(tier, ...)` builds the deterministic `_id` (`profile:<url>` / `name:<network>:<name>`); `build_record(...)` assembles a normalized document. **Stored classes are the CLASSIFIER classes only** (`organico`, `pagina_oficial`, `politico`, `comunidad`, `sitio_local/estatal/nacional`); `bot` and `influencer` are NOT stored — per the design spec they are derived at read time from `automation_score` / `followers` against tunable thresholds. Each record carries `classification` (+ confidence), `automation_score` (+ `automation_evidence`), `anonymity`, `followers`, the deterministic `features` dict, an `evidence_sample` (≤5 verbatim texts), activity counters (`n_comments`/`n_posts`/`n_distinct_parent_docs`/`pages_touched`), and provenance (`classified_at`, `evidence_as_of`, `llm_model`, `classifier_version`). `needs_reclassification(record)` gates re-work on materially new evidence (appearances newer than the stored `evidence_as_of`). `set_human_label(_id, automation, label, by)` attaches a reviewer judgment under the `human` key — classifier upserts `$set` only machine keys so they can never clobber it; consumers must read `effective_automation(record)` (max of machine score and human judgment) rather than `automation_score` (2026-07-21: accounts whose tells are profile-level are invisible to the feature pipeline; the WS-4 manual labels are pushed to stg with this mechanism). The store degrades to a no-op read path when Mongo is unreachable rather than raising at import.
- **`src/scripts/classify_users.py`** — the batch classifier CLI. Invocation:
  `python -m src.scripts.classify_users --pages "<source.name>" ... [--networks facebook tiktok] [--days 60] [--org 101 --entities 82 83] [--min-activity 2] [--official-pages "<name>" ...] [--apply]`. Default is a **dry run** (prints a review table + writes a JSON report to `cache/runs/`; writes to Mongo only with `--apply`). Stages:
  - **A — harvest (ES):** scans index `news` for posts where `source.name ∈ --pages` within `--days` (optional `news_type ∈ --networks`), collecting both post authors (`source.stats.profile_url`/`author_full_name`/`website_visits`/`author_profile_bio`, else falling back to name-tier on `source.name`) and every comment author from the top-level `comments` array (`comment_author`/`comment_text`/`comment_likes`/`comment_timestamp` + parent post `url`/`source.name`). ES connection reads `ELASTIC_HOST`/`ELASTIC_PORT`/`ELASTIC_AUTH` from the environment (https, `verify_certs=False`). Two dedup guards: an exact (author, text) duplicate within one post is a scraper double-capture; and the same (author, text, exact timestamp) on ANOTHER post is a **cloned post** (the same physical FB post ingested under two pfbid URL forms clones its whole comment list) — both count once, so neither can manufacture dup/burst/coordination signals. A real re-poster acts twice with differing timestamps and still counts.
  - **B — deterministic features (no LLM):** activity counters; text repetition (`max_duplicate_text_count`, `mean_pairwise_similarity` via `difflib` over a capped comment sample — no embeddings); like stats; burstiness (comments on *different* posts within a short window); name-shape anonymity signals. `compute_coordination(accounts)` then runs corpus-wide: different accounts commenting on the SAME post within `COORDINATION_WINDOW_SECONDS` (60s) form a pair; per-account `coordination_pair_posts`/`coordination_min_gap`/`coordination_partners` features are set **only when a pair exists** (features are part of the LLM cache key — unconditional keys would invalidate every cached account). `compute_automation(features)` derives a deterministic `automation_score` (copy-paste repetition saturates it — this is what flags Carlos-Martinez-style accounts regardless of the LLM). Low-volume arms from the WS-4 manual-label set (2026-07-21, `business_agent/customers/sjdr/ws4_manual_labels.json`): identical text on 2 distinct posts + a burst pair → 0.5 (the burst separates paste-bots from organic petitioners, who repeat their ask across days); a coordinated pair co-hitting ≥2 posts → 0.7 for both accounts; a single co-occurrence scores 0.5 only when the gap is ≤`COORDINATION_TIGHT_SECONDS` (30s), otherwise it is recorded but does not move the score. Second label round (same date): near-duplicate **slogan families** — texts ≥`NEAR_DUP_MIN_LEN` (15) clustered at difflib ratio ≥`NEAR_DUP_RATIO` (0.8); a 3+ cluster scores 0.5+, and a family spanning ≥2 pages scores 0.7 (`near_duplicate_pages` — organic petitioners stay on the mayor's page, operations follow the topic across venues); `posts_swept_30min` ≥4 (distinct posts inside a 30-min sliding window) → 0.5; `same_post_rapid_pairs` ≥2 with ≥3 comments (boilerplate multi-comment inside a minute on one post, the auto-greeter shape) → 0.5; `empty_comment_share` recorded as evidence (sticker spam). Short organic staples ("gracias", "amén") are below the near-dup length gate by design.
  - **Optional sentiment join (userdb):** only when `--org`/`--entities` and `DATABASE_URI` are given — reads `entities_documents_sentiments_org` comment rows (`doc_index='comment'`) and matches to harvested comments by `(parent_doc_id, timestamp-to-the-minute)`, folding per-account extremity share + dominant polarity into features. Degrades gracefully when absent.
  - **C — classification (cost-gated):** deterministic bypasses run first (name in `--official-pages` → `pagina_oficial`; a name/URL resolving to a known `SourcesManagement` domain → `sitio_*` by outlet geography) — **no LLM call**. Only accounts with `appearances >= --min-activity` and no deterministic class are sent to the LLM (batched via `src/oai/llm_core.py`'s cached `llm_cached_call`, Spanish prompt → strict-parsed JSON with an organico/low-confidence fallback); the rest default to `organico` with low confidence. Bump `CLASSIFIER_VERSION` to invalidate cached classifications after a prompt/feature change. Stored `automation_score = max(deterministic, LLM)`.
  - **D — output:** always prints a review table (sorted by `automation_score` desc) and writes a JSON report; `--apply` upserts into `SocialUsers`.

### Entry Point
- **`src/run_crawl_worker.py`** — the **crawl-run queue worker** (design `docs/db/crawl_tasks.md` §6.1; 2026-10-06). `python -m src.run_crawl_worker [--once]`. Consumes `crawl_run` messages (`{"type":"crawl_run","run_id",…,"org_id","trace_id","max_items","max_cost_usd","dry_run","params"}`) from `CRAWL_RUNS_QUEUE` on `CRAWL_RUNS_RABBIT_VIRTUAL_HOST` (locally `dev_crawl_runs` on `document_processing_dev`), prefetch `CRAWL_WORKER_CONCURRENCY` (default 1, **recommended 4**), manual ack per message after its run finishes (each run on its own thread with its own `heartbeat_at` beat, so the consuming connection keeps its heartbeats); a lost runs connection (`AMQPHeartbeatTimeout` / `StreamLostError` / `ConnectionClosed` / a failed connect) is reconnected by `consume_forever` with exponential backoff (2 s doubling, capped at `CRAWL_WORKER_RECONNECT_MAX_SECS`, default 60; reset after 5 min of healthy consuming) instead of ending the process (2026-10-07: tunnel blips killed the worker twice in one night and the whole scheduled round was reaped «not claimed»). Runs in flight keep going on their threads; their unacked messages are redelivered on the new connection and dropped as not claimable, so nothing runs twice. `--once` doesn't reconnect. Tests: `test_crawl_worker_reconnect.py`. Concurrency is threads in one process, not N processes: the on-disk caches (`cache/filter_cache.json`, `cache/users.json`, `cache/unknown_sources.json`) are shared in-process and saved under locks with merge + atomic replace (`src/helpers/atomic_json.py`), and document publishing (one pika connection) is serialized. Separate processes would each overwrite the others' cache files. Sizing: Apify STARTER = 32 concurrent actor runs / 64 GB; a run starts up to 3 actors of 1–4 GB, so 4 runs ≈ 12 actors / ≤ 48 GB and leaves room for hand runs. With N > 1 the worker reads `GET /v2/users/me/limits` once at startup (free) and lowers N to `min(maxConcurrentActorJobs // CRAWL_WORKER_ACTORS_PER_RUN (3), maxActorMemoryGbytes // (3 × CRAWL_WORKER_GB_PER_ACTOR (4)))` = 5 on STARTER; `CRAWL_WORKER_APIFY_LIMIT_CHECK=0` skips it. `--once` always runs 1. Concurrent runs also mean concurrent `usage_client.apify.run` admissions for the same org; each admits against the ledger on its own. Per message (`src/worker/runner.py::handle_message`): no/invalid `org_id` → ack + error log + best-effort `usage_blocks(path='worker:apify-client', tool='apify', kind=<msg kind>, reason='missing_org', search_id=query_id)`, the queued run is closed `failed`, nothing spent; claim `queued→running` (`UPDATE … WHERE status='queued'`) — a run already running/terminal (redelivery) is acked and dropped; userdb unreachable at claim → nack/requeue after `CRAWL_WORKER_DB_RETRY_SECS`. Then it **re-reads the task row** (DB is the source of truth; the message `params` are only diffed and logged as `stats.message_params_diff` — `min_date` is compared as an instant, since the backend sends the run's `window_since` in UTC with `period: null` while the worker reads it in the DB session's zone), builds kwargs with `CrawlTask.from_db_row()` + `to_actor_kwargs()` (same param path as the xlsx), applies the run's `window_since` (else the task's own window; with neither, **no date filter** — §2.8 R2, which also neutralizes `google_news`' default `timeframe="1d"` to `"all"` unless the task sets one), `override_filters` from `crawl_runs.params`, `max_results = min(run.max_items, task.max_results)` (also clamping `results_limit`/`max_articles`), validates `actor_params` against `crawl_actor_classes.params_schema` (empty schema = accept) and rejects cap-lifting `apify_input` keys. The actor gets a **`RecordingApifyClient`** (`src/worker/recording.py`): every `actor(id).call()` — main search and the utility actors (profiles/comments/video) — is recorded as soon as usage_client has settled and recorded it, as one `crawl_run_calls` row (`apify_run_id` unique → idempotent; `cost_usd` = usage_client's **settled** cost — `usage_cost_usd` / `usage_estimated` from `usage_client.apify.run`, the same reading as the `usage_events` row: Apify's `usageTotalUsd` once terminal, stable over two reads and the per-result charges cover the dataset items, ≤ 60 s; still unsettled → usage_client's own figure from the charged events / start + items × the actor's price with `estimated=true`, corrected later by `src/scripts/reconcile_costs.py`. Never the value `call()` returned: on 2026-10-07 that held only the actor-start charge — 9 calls recorded $0.0021 vs $0.6727 billed; `usage` = Apify `usage` + `chargedEventCounts` / `accountedChargedEventCounts` / `eventUsage` + `settled`; `items` = dataset `itemCount`; `purpose` from the pipeline stage via `instrument_actor`); search calls carry Apify `max_items` = the run's remaining paid-item budget (`max_items × len(search_params)` for `cap_scope='per_param'`), and every call `max_total_charge_usd` = remaining cost budget (min of message `max_cost_usd`, task `max_cost_usd_per_run`, run `admitted_usd`); a spent budget stops further calls (a call is skipped when the budget left is below the actor's start charge + one result, at the actor's real price from `usage_client.prices.apify_unit`). **Every call goes through `usage_client.apify.run`** (rate_limiting.md §2.7; `UsageMeter` in `recording.py`, no flag): one `UsageContext` per usage kind with `org_id` = `crawl_runs.org_id`, `user_id` = `requested_by`, `search_id` = `query_id`, `service='apify-client'`, `event_key='crawl-run:<run_id>'`, `kind` from the call's purpose (search → `crawl`, comments → `comments`, profiles → `profiles`, video/other → `crawl`). It admits the call against the org's `usage_limits` (Apify $15/day per org by default), passes Apify `max_items` = min(the run's caps above, admitted items) and `max_total_charge_usd` = min(the run's cost budget, admitted USD) plus the actor's own call kwargs, and records **one `usage_events` row per Apify run** (`event_id` `apify-client:crawl-run:<run_id>:<org>:<kind>:<apify run id>`), whose id lands in `crawl_run_calls.usage_event_id`. Enrichment calls are not capped by the run's search-item budget, but usage_client always sends a `max_items` (the admitted units; 1,000 at most when nothing tighter is known). `AdmissionRefused` (nothing admitted): `over_limit`/`per_request_cap` before any paid call → run **`blocked`** (terminal; `crawl_schedules` untouched, so the next tick retries); `ledger_unreachable` before any paid call → run released `running→queued` (`release_run`) and the message requeued after `CRAWL_WORKER_DB_RETRY_SECS` (if the release itself fails → `failed`); any refusal after a paid call → `partial`. The reason is in `error` and `stats.usage_refusal`; the `usage_blocks` row is written by usage_client (`crawl_runs.block_id` stays NULL — usage_client doesn't return the id); later calls of a refused run are refused locally. The ledger is `USAGE_DB_URI` (default `DATABASE_URI`; the `crawler` role has the usage grants, `2026-10-07_crawler_usage_grants_userdb.sql`), spool `USAGE_SPOOL_DIR` (default `cache/usage_spool`); the worker refuses to start without one. Documents are published through `publish_document` (the `RABBIT_*` document connection, opened lazily) — or, for `dry_run` / task `publish=false`, saved under `cache/runs/` with `output_path` recorded. Finish: `succeeded` / `partial` / `failed` (nothing bought). **`succeeded`** when the search call(s) succeeded and at most `max(1, 10%)` of the documents to publish (main docs + attached articles) failed to publish — those are in `stats.documents_failed` / `stats.documents_failed_urls` (first 20, ≤ 300 chars each) / `stats.documents_to_publish`; **`partial`** only for real partial work: Apify money spent and then a stage raised, the broker went away (`AMQPError`), a search call did not succeed, or more documents failed than tolerated (`runner.run_outcome`, 2026-10-07: a run with one bad attached link used to end `partial`). An attached article that can't be serialized is dropped (`stats.attached_news_dropped`), never a failure of its parent post. with the funnel (`items_paid` = search dataset items, `items_cached_filtered`, `items_dropped_keyword/date/language/location/llm`, `items_already_seen`, `items_new` = main docs published — would-be-published in dry runs, `attached_news_published`, `comments_fetched`, `profiles_scraped`, `newest_item_at`/`oldest_item_at`), `cost_usd` and `stats` (`funnel`, `effective_params`, `calls`, …). Cost writes (`crawl_run_calls` inserts, the final run update) never fail a run: on a DB error they go to the JSONL spool `CRAWL_WORKER_SPOOL_PATH` (default `cache/crawl_worker_spool.jsonl`) and are replayed at startup and around every message. A heartbeat thread bumps `heartbeat_at` every `CRAWL_WORKER_HEARTBEAT_SECS`. `trigger='schedule'` runs update `crawl_schedules` `last_run_id` / `last_success_at` only (skipped when the run was reaped meanwhile, or ended `blocked`); failure counting, retries, stagger and auto-pause belong to the poller's crawl scheduler (design §6.2.2); `kind='adhoc'` runs (no task row, `task_id` NULL; design §6.4) are built from the run row's `params.spec` with `CrawlTask.from_spec` — the DB row wins over the message, whose `params` are only diffed — and then follow exactly the crawl path (actor-class checks, `params_schema` / cap-lifting validation, window, budgets: cost cap = min(message `max_cost_usd`, spec `max_cost_usd_per_run`, `admitted_usd`), metering as `crawl`, funnel, cost); a bad or missing spec fails the run without spend, and there is no schedule bookkeeping (a missing-org block on an adhoc message is written with usage kind `crawl`); `kind='batch'` runs (design §6.5, plan `business_agent/docs/plans/crawl_batched_runs_2026-10.md`) are several tasks merged into one run: built with `CrawlTask.from_spec(params.spec, cache_key=params.task_id)` (`batch:<sha1>`; the spec is frozen at request time) plus the members from `crawl_run_tasks` (`CrawlDB.get_run_tasks`); `src/worker/batch.py::BatchContext` is set on the actor as `actor.batch` — the filter cache reads the batch key and every member's key and writes the batch key + the keys of the members a document belongs to, and it attributes documents to members by text match (X members: all their params; others: any; URL params by page/account name) → `crawl_run_tasks.items_matched` / `items_new` / `newest_item_at` / `cost_usd` (run cost × matched share), written before the run's finish (`update_run_tasks`, spooled); X batches send one `query` = the members' own clauses OR-ed (`batch_clauses` kwarg, `TwitterKeywordSearchActor.batch_query`); scheduled batch runs update every member's schedule; a bad batch (no members, member params outside the spec, non-`batch:` key, a `task_id`) fails without spend; `kind='comments'` runs read the posts linked by `crawl_comment_request_posts.run_id`, run `facebook_post_comments` with `max_comments` = the tier depth, write `comments_fetched` per post and move the request `approved→running→done`. ### Data Flow (staged pipeline)
```
Raw Apify actor output
  → create Documents (pure data mapping, no enrichment)
  → process_documents() pipeline (base class order; Instagram overrides to run location before user author):
      1. _filter_keywords      — cheapest, case-insensitive substring match on body+title against not_keywords
      2. _filter_date          — cheap, timestamp from API (resolves period to min_date)
      3. _enrich_content       — expensive (fetch_and_parse for news; social: fetch_attached_url via Post.fetch_attached_url() — fetches linked article, appends text, stores News on post.attached_news; download media stubs, OCR/transcription stubs)
      4. _filter_language      — cheap, needs body text from step 3
      5. _enrich_user_author   — always applies cached stats; scrapes profiles only when enrich_followers=True (bio, followers, full name, location text)
      6. _enrich_location      — news: SourcesManagement domain lookup (all author location fields); social: geocoding via add_locations() → location_ids
      7. _filter_location      — cheap, checks location_ids first (any geoid prefix match), falls back to author_location_id; keeps docs with no location data
      8. _filter_llm           — LLM-based filtering: sends batched text snippets (keyword context or first 250 chars) to LLM with a Spanish-language condition, keeps only indices returned. Skipped if llm_filter_condition not set
      9. _enrich_comments      — if get_comments: scrape via dedicated actor per platform
  → to_final_schema → publish to RabbitMQ
```

## Usage metering (rate limiting)

- **Role: records, and admits at run time.** The backend admits a crawl run at request time (`POST /crawl/runs/request` → `admit_api`, tool `apify`, partial admission allowed, stores `crawl_runs.admitted_usd`). ## Development Notes

- Python 3 with extensive type hints (`from __future__ import annotations`)
- Environment config via `.env` (Apify token, service endpoints). `src/actors/actor.py` calls `load_dotenv()` at import (found by walking up from the module's directory, so it works regardless of caller cwd) and `_get_apify_token()` resolves `APIFI_API_TOKEN` lazily when a real client is built (`src/helpers/metering.py::raw_apify_client`, the worker's factory) — a missing token raises a clear `RuntimeError` instead of letting an unauthenticated client reach the Apify API (which fails with a misleading `x402 payment header missing` error). An `ApifyActor` constructed without a client gets `UnmeteredApifyClient` (every Apify call refused: no org, no spend); pass a metered client to buy anything.
- MCP server configured in `.mcp.json` for Apify actor interaction
