# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

Apify Media Data Ingestion & Normalization Pipeline. Scrapes media/social data via Apify actors, normalizes it through a declarative schema system, and sends it to downstream services (RabbitMQ).

## Architecture

### Schema System (`src/schema/`)
Declarative, multi-stage data normalization framework:
- **`parse_object.py`** — Core `Parser` class that orchestrates: structure parsing (flatten/nest) → type conversion → default application → validation. Recurses into nested objects and into list-of-composite fields (see below) via `traverse_nested`.
- **`types.py`** — Type-specific parsers (`IntParser`, `FloatParser`, `StrParser`, `BoolParser`, `DateTimeParser`, `UrlParser`, `EnumStrParser`, `ListParser`) with parse/validate methods. Also exposes `extract_list_object_type(field_type)` which detects the `"List[Name]"` string syntax used to declare lists of composite items.
- **`schemas/news.py`** — NEWS_SCHEMA for articles/posts. `news_types = ["news", "x", "facebook", "impreso", "instagram", "linkedin", "radio", "tv"]` — the intermediate `type` field carries the actual platform and is validated by `EnumStr` against this list. Includes `location_ids` field (type list) for geocoded geoids, `location_author` (type `"LocationAuthor"`) as a nested object carrying author location fields, and `comments` (type `"List[Comment]"`) for per-post comment lists. Also defines `LOCATION_AUTHOR_SCHEMA` (unprefixed keys: `formatted_name`, `geoid`, `coords` (LocationCoords), `precision_level`, `level_1`/`level_2`/`level_3` and their `*_id` counterparts) and `COMMENT_SCHEMA` (`comment_text`, `comment_author`, `comment_author_url` — commenter profile URL, added 2026-07-21 to unblock WS-4 profile enrichment; scrapers return it, mappers now keep it — `comment_timestamp`, `comment_likes`) — each comment item is fully normalized: timestamps are parsed to `datetime`, likes are coerced to `int`. `require_url` reads `obj.get("type")` on the News record (URL required unless `type == "impreso"`). The intermediate `Document.data` still holds author location as flat `location_author_*` keys; `Document.to_final_schema()` collapses them (strips prefix) into the nested `location_author` dict before running `normalize_record`.
- **`schemas/source.py`** — SOURCE_SCHEMA for news sources/websites with crawl configuration

Key patterns: schemas support nested objects, `"List[CompositeType]"` string-typed lists of nested objects (e.g. `"comments": {"type": "List[Comment]"}`), context-aware default callbacks, conditional validation (e.g., URL required only when type != "impreso"), and timezone-aware datetime handling (Mexico City timezone).

### Models (`src/models/`)
Document hierarchy and source management:
- **`document.py`** — Base `Document` class. Holds intermediate schema data as `self.data` dict with `language` and `comments` fields. Provides `_empty_data()` (all intermediate fields as None/[], including `comments: []`), `detect_language()` (detects via `langdetect` and caches in `data["language"]`), `matches_language(code)`, `matches_min_date(dt)`, `matches_location(country_id)` (checks `location_ids` first — any geoid prefix match keeps doc; falls back to `author_location_id` when `location_ids` is empty; docs with no location data are kept), and `add_locations()` (writes geocoding results to `location_ids`; only writes author location fields if currently None, preserving SourcesManagement data) for pipeline filtering. Concrete `to_final_schema()` parses `self.data` against `NEWS_SCHEMA` and returns `{"type": "news", "message": parsed}` — the envelope type is always `"news"`; the inner `message.type` carries the platform.
- **`news.py`** — `News(Document)`. Represents a news article. `from_url(url)` class method creates a News from any URL, fetches and parses it, sets `data["source"]` via `SourcesManagement.get_source_name(domain)` when not already populated, returns News or None. `from_google_news(item)` class method creates a News from raw Apify dict (pure data mapping, no enrichment). `fetch_and_parse()` downloads HTML via `fetch_html()` (unpacking the `(html, final_url)` tuple), updates `self.data["url"]` to the final URL when it differs from the original (handling shortened/redirected URLs), then extracts content via `extract_article()` using the final URL, and updates `self.data` (title, body, author, media_urls, timestamp — only overwriting when the parser returned a non-empty value). `enrich_location(sources)` sets ALL author location fields (`location_author_formatted_name`, `location_author_geoid`, `location_author_coords`, `location_author_precision_level`, `location_author_level_1`/`level_2`/`level_3` and their IDs, plus `author_location_text`/`author_location_id`) from `SourcesManagement` domain lookup and tracks unknown sources. News articles do NOT geocode — location comes from SourcesManagement only. Uses the inherited `Document.to_final_schema()` (`type="news"` intermediate → envelope `{"type": "news", "message": parsed_news}`).
- **`post.py`** — Base `Post(Document)` class for social media posts. Overrides `to_final_schema()` to fill post-specific fallbacks (body, title, `fb_likes`) before delegating to `super().to_final_schema()` for schema parsing and envelope wrapping. Platform-specific subclasses handle data mapping and set `data["type"]` to the platform: `instagram`, `facebook`, `x`, `linkedin`. Shared `UsersManagement` singleton caches user profile data. Attribute: `attached_news: News | None` (initialized to `None`) stores the `News` object created when a linked article is fetched. Methods: `fetch_attached_url(url=None)` — when `url` is provided it is used directly; otherwise falls back to `self._raw.get("link")` (e.g. Facebook's `link` field) or the first external URL in the post body. Fetches and parses via `News.from_url()`, appends article text as `\n\n attached_url_text: <text>`, optionally copies source location to the post, stores the resulting `News` object on `self.attached_news`, and falls back to the parent post's `timestamp` when the fetched article still has no `timestamp` after parsing (the parser surfaces a date when one is present in the HTML, but some articles lack it) so the attached news isn't published with a null date. `_extract_first_external_url()` finds the first non-platform URL in the body. `enrich_location()` (geocode with UsersManagement cache), `needs_user_author_update(max_age_days)`, `apply_cached_user_author()` (applies cached `website_visits`, `author_full_name`, `author_profile_bio`, and `author_location_text`), `save_user_author_stats(stats)` (also writes `author_location_text` when present in stats). Intermediate schema includes `author_full_name` and `author_profile_bio` fields.
- **`instagram_post.py`** — `InstagramPost(Post)`. `from_instagram(item)` class method creates from raw Instagram Apify result, mapping caption, media URLs (via `_collect_media_urls`), engagement metrics, profile URL, and post type (Image, Sidecar, Story, Reel). `from_instagram_queenlike(item)` class method creates from a `queenlike_xystos/instagram-posts-reels-scraper---no-cookies` result: `taken_at` (epoch) → ISO `timestamp`, `caption` → `body`, `like_count` → `likes`, `reshare_count` → `shares` (the queenlike scraper actually returns share counts, unlike the default Instagram actors), `comment_count` → `n_comments`, `play_count` → `views`, `author.full_name`/`author.username` → `author`/`author_full_name`/`profile_url`, `author.follower_count` → `website_visits` (already embedded — no profile scrape needed for follower count). Post type is inferred via `_infer_queenlike_post_type` (`product_type=clips`/`reel` → Reel, `carousel_media`/`children` → Sidecar, `video_url` → Video, else Image). Media URLs collected via `_collect_queenlike_media_urls` (`video_url`, `thumbnail_url`, `image_url`, `display_url`, plus recursive `carousel_media`/`children`). In both mappers `source` carries the **account name** (full name, then username, falling back to `"Instagram"`) — the platform lives in `type`/`news_type`, and `source` must stay per-account so source-scoped searches and facets work (same convention as Facebook/X/LinkedIn and `TikTokPost.from_tiktok`, which uses nickname → username → `"TikTok"`).
- **`facebook_post.py`** — `FacebookPost(Post)`. `from_facebook(item)` class method creates from raw Facebook Posts Scraper result, mapping text, media (with OCR text appended as `image_text_N`), engagement metrics, and page name extracted from URL. Facebook post types: Photo, Video, Reel, Status. `from_facebook_search(item)` class method adapts `scrapeforge/facebook-search-posts` output to the same intermediate schema. Field mapping: `message_rich`/`message`/`text`/`content` → `body`; `timestamp` (epoch) → ISO `timestamp`; `reactions_count`/`likes_count`/`reactions.like` → `likes`; `reshare_count`/`shares_count` → `shares`; `comments_count` → `n_comments` (zero-safe via `_first_not_none()` so 0 isn't coerced to None); `author.name`/`author.url` → `author`/`profile_url`; `external_url` → carried on the raw object and passed explicitly into `Post.fetch_attached_url(url=…)` by `FacebookKeywordSearchActor._enrich_content`. `_infer_facebook_search_post_type()` checks `video`/`video_files`/`video_url`/`videos` → Video, then `image`/`image_url`/`images`/`album_preview` → Photo, else Status. `_collect_facebook_search_media_urls()` reads `image`, `video`, `thumbnail`, `video_thumbnail` (string fields), `album_preview[].image_file_uri`, `images[]`, and `video_files[]`/`videos[]`.
- **`twitter_post.py`** — `TwitterPost(Post)`. `from_twitter(item)` class method creates from raw `api-ninja/x-twitter-advanced-search` tweet: `body=full_text/text`, `author=user.name`, `author_profile_bio=user.description`, `author_location_text=user.location`, `profile_url=https://x.com/{screen_name}`, engagement metrics (likes, retweets, replies, views), media URLs from entities, and post type (original/reply/retweet/quote). Since bio and location come embedded in the tweet, `TwitterKeywordSearchActor` skips the `_enrich_user_author` stage entirely. Helpers: `_infer_tweet_type()`, `_collect_tweet_media_urls()`.
- **`linkedin_post.py`** — `LinkedInPost(Post)`. `from_linkedin(item)` class method creates from raw `harvestapi/linkedin-post-search` post: `body=text/content`, `author=author.name`, `author_profile_bio=author.headline`, `author_location_text=author.location`, `profile_url=author.linkedinUrl`, engagement metrics (`reactionsCount`/`repostsCount`/`commentsCount`), media URLs from `post.media`, and post type (video/image/text). `website_visits` is populated with `author.followersCount` when present (i.e. when `profileScraperMode="main"`). Helpers: `_infer_linkedin_post_type()`, `_collect_linkedin_media_urls()`.
- **`sources_management.py`** — `SourcesManagement` class. Single interface for all source-related operations. Reads sources from MongoDB (via `src/helpers/mongoconnection.py`) at module load and builds `_known_sources` set, `_domain_country_id` dict, and `_domain_source_name` dict (domain → `sitio`). If MongoDB is unavailable at load time, it uses an explicit empty catalog: news source/location enrichment is skipped, Mongo-backed source names/locations are not applied, and `cache/unknown_sources.json` is not updated. Methods: `get_domain(url)` extracts domain (tldextract-backed, strips `www` and ports), `is_known(domain)` checks known sources, `get_country_id(domain)` returns country_id (first 4 chars of `geoid`), `get_source_name(domain)` returns the known `sitio` or falls back to the domain name without TLD (e.g. `elfinanciero.com.mx` → `elfinanciero`), `get_location(domain)` and `_build_domain_location()` return a full location dict with all author location fields (`location_author_formatted_name`, `location_author_geoid`, `location_author_coords`, `location_author_precision_level`, `location_author_level_1`/`level_2`/`level_3` and their IDs), 
- **`news_parser/`** — Article enrichment pipeline (moved from `src/actors/news/news_parser/`):
  - **`load_url.py`** — `fetch_html(url)`: streaming HTTP download with size guard (10MB), retry, and browser UA headers. Returns a tuple `(html, final_url)` where `final_url` is the URL after following redirects (`r.url` from requests). Returns `(None, None)` on failure. **Timeouts are split** into a short `CONNECT_TIMEOUT` (10s, so dead/unroutable hosts fail fast and don't tie up an attempt) and a generous, per-attempt-escalating read timeout `READ_TIMEOUTS = (90, 120, 150)` (passed as `timeout=(connect, read)`); the same per-attempt read budget also caps total streaming time. Because a read timeout is only an upper bound on inter-byte wait, fast servers still return in their natural time — the generous first-attempt read budget costs them nothing while letting slow-but-succeeding origins behind slow CDNs (e.g. `oem.com.mx`, ~80s time-to-first-byte) succeed on the **first** attempt instead of dying on the old flat 15s cap and burning ~2 min across retries. `REQUESTS_TIMEOUT` is retained as an alias for `READ_TIMEOUTS[0]` for backwards compatibility.
  - **`parser.py`** — `extract_article(html, url)`: **multi-tier content extraction**, deterministic tiers first so full clean bodies come back instantly and the slow (~3 min) LLM tier stays a last resort. Cascade order:
    1. **Generic JSON-LD `articleBody` tier** (`_try_jsonld`) — scans all `application/ld+json` scripts (flattening top-level arrays and `@graph`) for the first `NewsArticle`/`Article`/`ReportageNewsArticle`/`BlogPosting`/… node (`_ARTICLE_LD_TYPES`) with a non-trivial `articleBody` (>= `MIN_JSONLD_BODY_LENGTH` = 200 chars); returns `{title=headline, body=articleBody, author, media_urls=image url(s), timestamp=datePublished}` directly. Site-agnostic; wins for any outlet that ships a full `articleBody`.
    2. **Domain-keyed extractor registry** (`_try_domain_extractor` → `_DOMAIN_EXTRACTORS`, mapping registrable domain → extractor). First entry: `oem.com.mx` → `_extract_oem`, which parses OEM's (Organización Editorial Mexicana) Next.js **RSC flight stream** (`self.__next_f.push([1,"…"])` chunks — the visible DOM only holds related-article sidebars, and OEM JSON-LD has no `articleBody`). It JSON-string-unescapes each chunk (correct UTF-8 accents — never `unicode_escape`, which mojibakes `año`→`aÃ±o`), collects every `storyline_paragraph` value node in document order pairing each with its enclosing node's `publishedAt`, keeps only paragraphs whose date matches the article's (JSON-LD `datePublished`, else the mode — this drops the trailing author-bio card carrying a different date), drops the injected newsletter CTA and verbatim repeats, reassembles the body, and validates extracted word count against JSON-LD `wordCount` (rejects a fragment < 0.3×). Metadata (title/author/date/image) comes from JSON-LD. Returns `None` on any failure so the cascade continues unchanged.
    3. **NewsPlease** (+ `newspaper4k` gap-fill), guarded by `_has_meaningful_content` / the related-content guards below.
    4. **LLM fallback** (via `src/oai/llm_core.py`) when everything above fails.
    Both deterministic tiers log at INFO which tier produced the body (so tier usage is measurable in run logs). Returns `{title, body, author, media_urls, timestamp}` or None. `timestamp` is sourced from JSON-LD `datePublished`, NewsPlease's `date_publish`, newspaper's `publish_date`, or the LLM's `published_at` field (ISO 8601), and may be a `datetime` or string — the schema's `DateTimeParser` accepts both. Requires body >= 200 chars for meaningful content. `_has_meaningful_content` also rejects bodies whose text looks like a related-posts list, via two heuristics that force the LLM tier: (1) `_looks_like_related_posts_list` — 3+ case-insensitive hits of "Ver más"/"Leer más"/"Read more"/"See more"/"Continue reading"/"Saber más"/"Más información" (catches WordPress page-builder loop blocks, e.g. Breakdance `bde-loop-item`/`ee-post-content`); (2) `_looks_like_section_label_list` — catches the OEM (Organización Editorial Mexicana) variant that evades (1): the extracted "body" is a stack of `SECTION\nHeadline\nDek` triples, so it fires when known section-label lines (LOCAL/POLICIACA/CULTURA/DEPORTES/FINANZAS/NACIONAL/... — see `_SECTION_LABELS`) appear as standalone lines 3+ times, **or** any short line (<=40 chars) repeats verbatim 3+ times. Both are structural signals (label alone on its own line / verbatim repetition), so a real article merely mentioning those words inline is not rejected.

### Actors System (`src/actors/`)
Apify actor integrations for data scraping:
- **`actor.py`** — Base `ApifyActor` class. Wraps `ApifyClient`, provides `run_actor()` for executing actors, and `process_documents(docs, **kwargs)` — a staged pipeline that runs: `_filter_keywords` → `_filter_date` → `_enrich_content` → `_filter_language` → `_enrich_user_author` → `_enrich_location` → `_filter_location` → `_filter_llm` → `_enrich_comments`. User author enrichment runs before location so that cached profile data (including `author_location_text`) is available for geocoding. Subclasses can override `process_documents()` to change the pipeline order (e.g. Instagram overrides to run location before user author). `_filter_keywords` filters out documents matching any `not_keywords` (case-insensitive substring on body+title). `_filter_date` resolves `period` (d/w/m) to `min_date` if no explicit `min_date` is given. `_filter_llm` caches each document's keep/drop decision per `(url, condition, snippet_max_len)` (via `cache_get`/`cache_set` in `src/oai/llm_core.py`, tag `llm_filter`, field `keep`): documents with a cached decision are resolved up front and only undecided ones are sent to the LLM, batched (`LLM_FILTER_BATCH_SIZE`) with snippets (keyword-context or first 250 chars) under a Spanish-language `llm_filter_condition`; the LLM returns the indices to keep and each new decision is written back. Because the key is URL-based (not batch-based), a decision is reused regardless of batching and shared across tasks with the same condition; `override_filters=True` bypasses the cache read and re-evaluates. URL-less docs are never cached. The batch call itself still uses `llm_cached_call` (tag `llm_filter_batch`) as a content-addressed fallback. `search_params` is stored as `self.search_params` by each actor's `search()` for keyword-context snippet extraction. `_enrich_user_author` is no-op by default; subclasses override to enrich posts with author profile data. Cached user stats are always applied regardless of `enrich_followers` flag; the flag only gates the expensive Apify scraping call. `_enrich_comments` is no-op by default; subclasses override to scrape comments via dedicated actors. Defines the interface: `search(search_params, **kwargs)`. Subclasses must set `actor_id`.
- **`instagram/hashtags.py`** — `InstagramHashtagActor` extending `ApifyActor`. Overrides `process_documents()` to use a different pipeline order: location enrichment runs before user author enrichment (body-text geocoding doesn't depend on profile data). Implements `search(search_params)` to scrape hashtags via Apify actor `reGe1ST3OBgYZSsZJ`. Creates `InstagramPost` objects via `InstagramPost.from_instagram(item)`, then calls `process_documents()`. Overrides `_enrich_content`: loops over posts calling `doc.fetch_attached_url(self.sources_manager)` directly (URL extraction, fetch/parse via `News.from_url()`, text append, location copy, storing the `News` object on `post.attached_news` — all handled by `Post.fetch_attached_url()`), plus Instagram-specific stubs: `_download_images`, `_download_video`, `_add_text_from_images`, `_add_subtitles`, `_add_ai_transcription`. Overrides `_enrich_user_author` to always apply cached stats and enrich posts with author profile data (bio, followers, full name) via `apify/instagram-profile-scraper` when `enrich_followers=True`. Overrides `_enrich_comments` to scrape comments via `apify/instagram-comment-scraper` when `get_comments=True`. Returns `List[InstagramPost]`.
- **`instagram/profile_posts.py`** — `InstagramProfilePostsActor` extending `ApifyActor`. Implements `search(search_params)` to scrape posts from Instagram profile URLs via Apify actor `shu8hvrXbJbY3Eb9W`. `search_params` are profile URLs (e.g. `https://www.instagram.com/username/`). Creates `InstagramPost` objects via `InstagramPost.from_instagram(item)`. Same pipeline order as `InstagramHashtagActor` (location before user author). Implements `_download_video` using `igview-owner/instagram-video-downloader`: collects URLs of Video/Reel posts, bulk-calls the downloader actor, downloads files with URL-hash-based caching to `cache/media/instagram/` (configurable via `video_dir` kwarg), and sets `doc.data["video_filename"]` to the local path. Module-level helpers: `_url_hash(url)`, `_video_exists(target_dir, hash)`, `_download_video_file(download_url, target_dir, hash, ext)`. Other enrichment stubs (`_download_images`, `_add_text_from_images`, `_add_subtitles`, `_add_ai_transcription`) raise `NotImplementedError`. Same `_enrich_user_author` and `_enrich_comments` as `InstagramHashtagActor`. Returns `List[InstagramPost]`.
- **`instagram/profile_queenlike.py`** — `InstagramProfileQueenlikeActor` extending `InstagramProfilePostsActor`. Wraps the `queenlike_xystos/instagram-posts-reels-scraper---no-cookies` actor. `search_params` are bare usernames (e.g. `"nina.deloto"`); leading `@` and any `https://www.instagram.com/<user>/` URL form are tolerated and stripped via `_normalize_username`. The actor only accepts a single `username` per run, so `search()` loops over inputs and dedupes results by post URL. Run input: `{"username", "max_items", "scrape_type", "output_mode"}` (defaults: `max_items=results_limit`/`max_results`, `scrape_type="posts"`, `output_mode="clean"`). Creates `InstagramPost` objects via `InstagramPost.from_instagram_queenlike(item)`. Inherits the rest of the pipeline (location-before-user-author order, `_download_video`, `_enrich_user_author`, `_enrich_comments`) unchanged from `InstagramProfilePostsActor`. Main reason to pick this actor over the default: the response contains `reshare_count` (mapped to `shares`) and `author.follower_count` (mapped to `website_visits`) on every post, so share counts are surfaced and follower stats arrive for free without a separate profile scrape. Returns `List[InstagramPost]`.
- **`facebook/posts.py`** — `FacebookPagePostsActor` extending `ApifyActor`. Implements `search(search_params)` to scrape Facebook page posts via `apify/facebook-posts-scraper`. `search_params` are Facebook page URLs. Creates `FacebookPost` objects via `FacebookPost.from_facebook(item)`, then calls `process_documents()`. Overrides `process_documents()` to run the base pipeline and then, when `fetch_attached_url=True`, retry URL attachment for any post still missing `attached_news` by scanning the first scraped comment for an external URL (Facebook pages often drop the article link into the first comment rather than the post body; the retry runs after `_enrich_comments` so comments are already populated). Overrides `_enrich_content`: loops over posts calling `doc.fetch_attached_url(self.sources_manager)` directly, plus Facebook-specific stubs: `_download_images`, `_download_video`, `_add_text_from_images`, `_add_subtitles`, `_add_ai_transcription`. Overrides `_enrich_user_author` to always apply cached stats and enrich posts with page profile data (page likes as follower proxy, full name, bio, location text) via `FacebookProfileActor` when `enrich_followers=True`. Follows the same pattern as Instagram: apply cached stats (always) → collect stale profiles → bulk scrape (only when `enrich_followers=True`) → index by page name → map results back → `save_user_author_stats()`. `stats_max_age_days` configurable (default 90). Overrides `_enrich_comments` to scrape comments via `FacebookCommentsActor` (`apify/facebook-comments-scraper`) when `get_comments=True`. Returns `List[FacebookPost]`.
- **`facebook/post_comments.py`** — `FacebookPostCommentsActor` extending `ApifyActor`. **Comments-on-demand** (agent_framework §5.3 / enablement item 12): a task-addressable, targeted comment fetch for a list of *individual* Facebook post/video/photo/reel URLs (not a page/keyword crawl). Registry key `facebook_post_comments`. `search(search_params, max_comments=15)` — `search_params` are the post URLs; one bulk call to `FacebookCommentsActor` (`apify/facebook-comments-scraper`, `resultsLimit=max_comments`) scrapes all URLs, `group_by_post_url` maps+groups the comments, and one minimal `FacebookPost` is built per input URL. **Deliberately bypasses `process_documents` entirely** — no keyword/date/LLM filters, no attached-URL fetch, no geocoding, no author-profile scrape, and (critically) no `_filter_existing_in_elasticsearch` (which would drop every URL, defeating the purpose). Each built doc sets `url` = the input URL **verbatim** (it is the ES `_id` and gp3's merge key), `type=facebook`, `comments` = grouped list, and `source`/`author`/`profile_url` derived from the URL page slug (`_extract_facebook_page_name`, falling back to `"Facebook"`); `timestamp` is set to fetch-time only to satisfy the required-timestamp schema constraint. **Engagement stats (likes/shares AND `n_comments`) are intentionally left unset** — gp3's engagement update overwrites `n_comments` with whatever the doc carries, and the scraped count is only a *sample* (capped at `max_comments`) usually smaller than the post's true total, so sending it would clobber a truer value downward; leaving all three null makes gp3 preserve the existing stats (verified live: likes/shares/n_comments preserved while the comments merge in). **The URL form must match the stored ES `_id` exactly** — e.g. the mayor's video is stored with a *trailing slash* (`.../videos/841969948996525/`); pass the URL exactly as ingested or the merge silently no-ops. When published, gp3's `update_social_news_engagement` recognizes the existing URL `_id` in the `news` index and **merges** the new comments (deduped) into the existing document in place. Scraper output is matched back to the input URL by exact key, then by a normalized key (`_normalize_post_url`: drop scheme/`www.`/query/fragment/trailing slash), then — for a single input URL — by assigning all scraped comments to it (handles the scraper canonicalizing `postUrl`, e.g. `m.facebook.com`). Intended dispatch: a `tasks.xlsx` row or ephemeral queue message with `actor_class=facebook_post_comments`, `search_params=[post urls]`, `max_comments=N`, `publish=TRUE`.
- **`facebook/profiles.py`** — `FacebookProfileActor`, a lightweight utility class (does NOT inherit from `ApifyActor`). Wraps `apify/facebook-pages-scraper` for page profile lookups. Not a search-task actor and NOT in the actor registry. `__init__(self, client)` accepts an existing `ApifyClient`. `scrape_pages(page_urls)` calls the actor with `startUrls` and returns raw results. `map_profile(raw)` (static method) maps raw output to a stats dict: `followers` (preferred) or `likes` → `website_visits`; `title` (or `personalProfile.name` when `title` is empty) → `author_full_name`; `info` (list joined with newline) → `author_profile_bio`; `address` → `current_city`/`CURRENT_CITY` → `hometown`/`HOMETOWN` (with "Lives in "/"From " prefixes stripped) → `author_location_text`. Also stores `categories`, `rating`, `email`, `phone`, `website`, and the full raw response as `_raw_profile`. Module helper `index_profiles_by_page_name(raw_profiles)` builds a `{page_name → profile}` lookup keyed by every name representation (`pageName`, plus names extracted from `facebookUrl` and `pageUrl`) so callers can resolve a profile by whichever key matches the post's `profile_url` — both `FacebookPagePostsActor._enrich_user_author` and `FacebookKeywordSearchActor._enrich_user_author` use it.
- **`facebook/comments.py`** — `FacebookCommentsActor`, a lightweight utility class (does NOT inherit from `ApifyActor`). Wraps `apify/facebook-comments-scraper` for post comment scraping. Not a search-task actor and NOT in the actor registry. `__init__(self, client)` accepts an existing `ApifyClient`. `scrape_comments(post_urls, max_comments)` calls the actor with `startUrls` and `resultsLimit` and returns raw results. `map_comment(raw)` (static method) maps raw output to the common comments schema: `text` → `comment_text`, `profileName` → `comment_author`, `date` → `comment_timestamp`, `profileUrl` → `comment_author_url`, `likesCount` → `comment_likes`. `group_by_post_url(raw_comments)` groups mapped comments by post URL (falls back from `postUrl` to `facebookUrl`).
- **`facebook/keyword_search.py`** — `FacebookKeywordSearchActor` extending `ApifyActor`. Implements `search(search_params)` to scrape Facebook posts by keyword/phrase via `scrapeforge/facebook-search-posts` ($0.00259/result). The actor accepts a single query per run, so `search()` loops over each entry in `search_params` and dedupes by `post_url`. Resolves `start_date`/`end_date` from `period`/`min_date`. Creates `FacebookPost` objects via `FacebookPost.from_facebook_search(item)`, then calls `process_documents()`. **Overrides `process_documents()`** to run `_filter_llm` (both passes) right after `_filter_language`, before `_enrich_user_author`/`_enrich_location`/`_filter_location`/`_enrich_comments`, so LLM-rejected posts skip the expensive author scrape, geocoding, and comment scrape. Overrides `_enrich_content`: when `fetch_attached_url=True`, calls `doc.fetch_attached_url(url=doc._raw.get("external_url"))` so the linked-article URL surfaced by the search actor is used directly (the post body usually doesn't contain the link). Overrides `_enrich_user_author` to always apply cached stats and, when `enrich_followers=True`, bulk-scrape stale page profiles via `FacebookProfileActor` (`apify/facebook-pages-scraper`) — same pattern as `FacebookPagePostsActor`: apply cached stats (always) → collect stale profiles → bulk scrape (only when `enrich_followers=True`) → index by page name → map results back → `save_user_author_stats()` (persists to `cache/users.json`). `stats_max_age_days` configurable (default 90). `enrich_author_after_likes` (int, optional): only scrape profiles for posts whose `likes` exceed this threshold (cached stats still apply to all). Overrides `_enrich_comments` to reuse `FacebookCommentsActor` when `get_comments=True`; `get_comments_after_likes` (int, optional): only scrape comments for posts whose `likes` exceed this threshold. Returns `List[FacebookPost]`.
- **`twitter/keyword_search.py`** — `TwitterKeywordSearchActor` extending `ApifyActor`. Implements `search(search_params)` to search X (Twitter) via `api-ninja/x-twitter-advanced-search` ($0.00035/result). Classifies each search param into `contentKeywords` (plain tokens), `contentExactPhrases` (entries with spaces), or `contentHashtags` (entries starting with `#`); strips surrounding quotes before classification. Forwards `contentLanguage` when `language` normalizes to a supported ISO code, `timeSince` (from `min_date`) or `timeWithinTime` (from `period`: d→1d, w→7d, m→30d), and `search_type="Latest"`. Single API call for all queries. Creates `TwitterPost` objects via `TwitterPost.from_twitter(item)`. **Overrides `process_documents()` to drop `_enrich_user_author` entirely** — the tweet already carries author name, bio, location, and follower counts on the `user` object. `_enrich_comments` is a no-op (X replies are themselves tweets). Returns `List[TwitterPost]`.
- **`linkedin/keyword_search.py`** — `LinkedInKeywordSearchActor` extending `ApifyActor`. Implements `search(search_params)` to search LinkedIn posts via `harvestapi/linkedin-post-search` ($0.0015–$0.002/result). Single actor call with `searchQueries=search_params`, `maxPosts=results_limit`, `sortBy="date"`, `profileScraperMode="short"`, and `postedLimit` mapped from `period` (d→`24h`, w→`week`, m→`month`). Creates `LinkedInPost` objects via `LinkedInPost.from_linkedin(item)`. Overrides `process_documents()` with Instagram-style order (location before user_author). Overrides `_enrich_user_author` to apply cached stats always and, when `enrich_followers=True`, re-call the same actor with `authorUrls=<profile URLs needing update>` and `profileScraperMode="main"` to fetch follower counts. Overrides `_enrich_comments` when `get_comments=True` by re-calling the actor with `scrapeComments=True`, `maxComments`, and post URLs as `authorUrls`. Returns `List[LinkedInPost]`.
- **`news/news_scraper.py`** — `GoogleNewsActor` extending `ApifyActor`. Implements `search(search_params)` to scrape Google News via actor `3Z6SK7F2WoPU3t2sg`. Defaults to Mexico/Spanish (`MX:es-419`). Accepts optional `topics` through `actor_params` as a string or list of Google News topic keys: `WORLD`, `NATION`, `BUSINESS`, `TECHNOLOGY`, `ENTERTAINMENT`, `SPORTS`, `SCIENCE`, `HEALTH`. Creates `News` objects via `News.from_google_news(item)` (pure data mapping), then calls `process_documents()`. Overrides `_enrich_content` (delegates to `News.fetch_and_parse()`) and `_enrich_location` (delegates to `News.enrich_location(sources_manager)`). Returns `List[News]`.

### Helpers (`src/helpers/`)
- **`language.py`** — `normalize_language(raw)`: maps language identifiers to ISO 639-1 codes. Handles full names (`"spanish"` → `"es"`), BCP 47 (`"es-MX"` → `"es"`), Google News format (`"MX:es-419"` → `"es"`), and passthrough (`"es"` → `"es"`).
- **`html_cleaner.py`** — `clean_html(html)`: single-pass HTML cleaner that strips script/style/noscript/SVG/iframe/head/comments/base64 data URIs, removes non-essential attributes (keeps href/src/alt/title/datetime/content/name/property), unwraps nav/footer/aside/form tags, and collapses whitespace. Designed to reduce token count before LLM parsing.
- **`mongoconnection.py`** — MongoDB connection setup. Reads credentials from env vars (`MONGO_USER`, `MONGO_PASSWORD`, `MONGO_HOST`, `MONGO_PORT`, `MONGO_AUTHDB`), provides `mongoconn` singleton client and `get_mongo_connection()`. Used by `SourcesManagement` to load source data.
- **`serialization.py`** — canonical wire serialization: `serialize_message(payload)` (JSON with ISO-8601 `T`-separator datetimes) and `publish_document(doc)` (`to_final_schema()` → serialize → publish). ALL document publishes must go through this — never hand-roll `json.dumps` (a `default=str` publisher emitted space-format datetimes that ES rejects, poison-looping gp3's engagement merge; 2026-07-21 incident). Import-safe (no connection at import), unlike `rabbitmq.py`.
- **`rabbitmq.py`** — `RMQ` class wrapping `pika.BlockingConnection` for RabbitMQ publishing. Handles connection/channel lifecycle, auto-reconnect on AMQP errors, and exposes module-level `publish()` and `close_client()` functions via a singleton instance. Config from env vars (`RABBIT_HOST`, `RABBIT_PORT`, `RABBIT_USER`, `RABBIT_PASSWORD`, `RABBIT_EXCHANGE`, `RABBIT_QUEUE`, `RABBIT_VIRTUAL_HOST`).

### Task System
- **`src/models/crawl_task.py`** — `CrawlTask` dataclass representing a single crawl job. Fields include `period` (d/w/m, mutually exclusive with `min_date`), `get_comments` (bool), `max_comments` (int, default 15), `not_keywords` (list, pipe-separated), and `llm_filter_condition` (str, Spanish-language filtering condition for LLM-based filtering). `from_csv_row()` parses a row dict (search_params as comma-separated, not_keywords as pipe-separated, actor_params as JSON). `to_actor_kwargs()` merges common + actor-specific params. `load_tasks(xlsx_path)` reads Excel (.xlsx) and returns enabled tasks.
- **`tasks.xlsx`** — Excel file defining all crawl jobs. Columns: `actor_class`, `search_params`, `country_id`, `language`, `min_date`, `period`, `max_results`, `enabled`, `publish`, `get_comments`, `max_comments`, `not_keywords`, `llm_filter_condition`, `theme`, `actor_params`. `theme` is used by `run_searches.py` to filter tasks to a single theme (set via `CURRENT_THEME` constant). `classify_users` (default FALSE) opts the task's scope into the post-run WS-4 user-classification pass (page tasks contribute their page's source name, keyword tasks their search_params as phrases); `official_page` (default FALSE) marks page tasks whose account belongs to the customer, feeding the deterministic `pagina_oficial` bypass. Both are per-customer opt-ins — leave FALSE for customers that don't need account characterization.
- **`src/actors/__init__.py`** — Actor registry mapping string keys (`google_news`, `instagram_hashtags`, `instagram_profile_posts`, `instagram_profile_queenlike`, `facebook_page_posts`, `facebook_post_comments`, `facebook_keyword_search`, `twitter_keyword_search`, `linkedin_keyword_search`, `tiktok_posts`) to actor classes. `get_actor(actor_class)` instantiates by key.

### Social-account characterization (WS-4)

A read-time classification layer for social authors: a Mongo-backed per-account store plus a batch classifier that harvests evidence from Elasticsearch, computes deterministic features, optionally joins userdb sentiment, and LLM-classifies only accounts with enough activity. **Reports look accounts up in Mongo at read time and join them onto the (immutable) ES documents — nothing is written to ES.** Grounding: `reports/event_report/docs/social_report_design.md` §1 and `business_agent/customers/sjdr/plan.md` WS-4.

- **`src/models/social_users.py`** — `SocialUsers`, a CRUD wrapper over the `SocialUsers` Mongo collection (same DB as `CrawlersAll`; name from `MONGO_DB_NEWS_SOURCES`, reuses `src/helpers/mongoconnection.py`). **Two-tier identity, one document per account**: tier `"profile"` (post authors) keyed by a canonical, normalized `profile_url`; tier `"name"` (comment-only authors) keyed by `(network, normalized_name)` where `normalize_name` casefolds, collapses whitespace and strips accents. Name-tier records carry a lower `identity_confidence` ceiling (best-effort display-name identity). `account_id(tier, ...)` builds the deterministic `_id` (`profile:<url>` / `name:<network>:<name>`); `build_record(...)` assembles a normalized document. **Stored classes are the CLASSIFIER classes only** (`organico`, `pagina_oficial`, `politico`, `comunidad`, `sitio_local/estatal/nacional`); `bot` and `influencer` are NOT stored — per the design spec they are derived at read time from `automation_score` / `followers` against tunable thresholds. Each record carries `classification` (+ confidence), `automation_score` (+ `automation_evidence`), `anonymity`, `followers`, the deterministic `features` dict, an `evidence_sample` (≤5 verbatim texts), activity counters (`n_comments`/`n_posts`/`n_distinct_parent_docs`/`pages_touched`), and provenance (`classified_at`, `evidence_as_of`, `llm_model`, `classifier_version`). `needs_reclassification(record)` gates re-work on materially new evidence (appearances newer than the stored `evidence_as_of`). `set_human_label(_id, automation, label, by)` attaches a reviewer judgment under the `human` key — classifier upserts `$set` only machine keys so they can never clobber it; consumers must read `effective_automation(record)` (max of machine score and human judgment) rather than `automation_score` (2026-07-21: accounts whose tells are profile-level are invisible to the feature pipeline; the WS-4 manual labels are pushed to stg with this mechanism). The store degrades to a no-op read path when Mongo is unreachable rather than raising at import.
- **`src/scripts/classify_users.py`** — the batch classifier CLI. Invocation:
  `python -m src.scripts.classify_users --pages "<source.name>" ... [--networks facebook tiktok] [--days 60] [--org 101 --entities 82 83] [--min-activity 2] [--official-pages "<name>" ...] [--apply]`. Default is a **dry run** (prints a review table + writes a JSON report to `cache/runs/`; writes to Mongo only with `--apply`). Stages:
  - **A — harvest (ES):** scans index `news` for posts where `source.name ∈ --pages` within `--days` (optional `news_type ∈ --networks`), collecting both post authors (`source.stats.profile_url`/`author_full_name`/`website_visits`/`author_profile_bio`, else falling back to name-tier on `source.name`) and every comment author from the top-level `comments` array (`comment_author`/`comment_text`/`comment_likes`/`comment_timestamp` + parent post `url`/`source.name`). ES connection reads `ELASTIC_HOST`/`ELASTIC_PORT`/`ELASTIC_AUTH` from the environment (https, `verify_certs=False`). Two dedup guards: an exact (author, text) duplicate within one post is a scraper double-capture; and the same (author, text, exact timestamp) on ANOTHER post is a **cloned post** (the same physical FB post ingested under two pfbid URL forms clones its whole comment list) — both count once, so neither can manufacture dup/burst/coordination signals. A real re-poster acts twice with differing timestamps and still counts.
  - **B — deterministic features (no LLM):** activity counters; text repetition (`max_duplicate_text_count`, `mean_pairwise_similarity` via `difflib` over a capped comment sample — no embeddings); like stats; burstiness (comments on *different* posts within a short window); name-shape anonymity signals. `compute_coordination(accounts)` then runs corpus-wide: different accounts commenting on the SAME post within `COORDINATION_WINDOW_SECONDS` (60s) form a pair; per-account `coordination_pair_posts`/`coordination_min_gap`/`coordination_partners` features are set **only when a pair exists** (features are part of the LLM cache key — unconditional keys would invalidate every cached account). `compute_automation(features)` derives a deterministic `automation_score` (copy-paste repetition saturates it — this is what flags Carlos-Martinez-style accounts regardless of the LLM). Low-volume arms from the WS-4 manual-label set (2026-07-21, `business_agent/customers/sjdr/ws4_manual_labels.json`): identical text on 2 distinct posts + a burst pair → 0.5 (the burst separates paste-bots from organic petitioners, who repeat their ask across days); a coordinated pair co-hitting ≥2 posts → 0.7 for both accounts; a single co-occurrence scores 0.5 only when the gap is ≤`COORDINATION_TIGHT_SECONDS` (30s), otherwise it is recorded but does not move the score. Second label round (same date): near-duplicate **slogan families** — texts ≥`NEAR_DUP_MIN_LEN` (15) clustered at difflib ratio ≥`NEAR_DUP_RATIO` (0.8); a 3+ cluster scores 0.5+, and a family spanning ≥2 pages scores 0.7 (`near_duplicate_pages` — organic petitioners stay on the mayor's page, operations follow the topic across venues); `posts_swept_30min` ≥4 (distinct posts inside a 30-min sliding window) → 0.5; `same_post_rapid_pairs` ≥2 with ≥3 comments (boilerplate multi-comment inside a minute on one post, the auto-greeter shape) → 0.5; `empty_comment_share` recorded as evidence (sticker spam). Short organic staples ("gracias", "amén") are below the near-dup length gate by design.
  - **Optional sentiment join (userdb):** only when `--org`/`--entities` and `DATABASE_URI` are given — reads `entities_documents_sentiments_org` comment rows (`doc_index='comment'`) and matches to harvested comments by `(parent_doc_id, timestamp-to-the-minute)`, folding per-account extremity share + dominant polarity into features. Degrades gracefully when absent.
  - **C — classification (cost-gated):** deterministic bypasses run first (name in `--official-pages` → `pagina_oficial`; a name/URL resolving to a known `SourcesManagement` domain → `sitio_*` by outlet geography) — **no LLM call**. Only accounts with `appearances >= --min-activity` and no deterministic class are sent to the LLM (batched via `src/oai/llm_core.py`'s cached `llm_cached_call`, Spanish prompt → strict-parsed JSON with an organico/low-confidence fallback); the rest default to `organico` with low confidence. Bump `CLASSIFIER_VERSION` to invalidate cached classifications after a prompt/feature change. Stored `automation_score = max(deterministic, LLM)`.
  - **D — output:** always prints a review table (sorted by `automation_score` desc) and writes a JSON report; `--apply` upserts into `SocialUsers`.

### Entry Point
- **`src/run_searches.py`** — Main orchestrator: loads tasks from `tasks.xlsx`, filters by `CURRENT_THEME` (module-level constant, currently `"orizaba"`), dispatches each to the appropriate actor by calling `actor.search()` directly, and publishes to RabbitMQ. The module-level `OVERRIDE_FILTERED_CACHE` constant (default `False`), when set `True`, forces `override_filters=True` into every task's actor kwargs so the cached filtered-out documents are dismissed for all actors and all filters re-run from scratch. All filtering and enrichment is handled by actors via `ApifyActor.process_documents()`. After the task loop, tasks flagged `classify_users` trigger one aggregated user-classification pass (`src/scripts/classify_users.py::run` with `--apply` semantics, scope derived from the flagged tasks); its failure never affects crawl results. Before publishing, each document is expanded into itself + its `attached_news` (when present), so linked articles attached to social posts are parsed via `News.to_final_schema()` and published alongside the parent post.

### Data Flow (staged pipeline)
```
Raw Apify actor output
  → create Documents (pure data mapping, no enrichment)
  → process_documents() pipeline (base class order; Instagram overrides to run location before user author):
      1. _filter_keywords      — cheapest, case-insensitive substring match on body+title against not_keywords
      2. _filter_date          — cheap, timestamp from API (resolves period to min_date)
      3. _enrich_content       — expensive (fetch_and_parse for news; social: fetch_attached_url via Post.fetch_attached_url() — fetches linked article, appends text, stores News on post.attached_news; download media stubs, OCR/transcription stubs)
      4. _filter_language      — cheap, needs body text from step 3
      5. _enrich_user_author   — always applies cached stats; scrapes profiles only when enrich_followers=True (bio, followers, full name, location text)
      6. _enrich_location      — news: SourcesManagement domain lookup (all author location fields); social: geocoding via add_locations() → location_ids
      7. _filter_location      — cheap, checks location_ids first (any geoid prefix match), falls back to author_location_id; keeps docs with no location data
      8. _filter_llm           — LLM-based filtering: sends batched text snippets (keyword context or first 250 chars) to LLM with a Spanish-language condition, keeps only indices returned. Skipped if llm_filter_condition not set
      9. _enrich_comments      — if get_comments: scrape via dedicated actor per platform
  → to_final_schema → publish to RabbitMQ
```
